# 📖 架构设计笔记：厚工具层 (Fat Tools) 与工业级上下文管理

## 一、 核心架构哲学：从“哑工具”到“智能工具”

在传统的 Agent 开发中，工具通常是“哑的（Thin/Dumb）”，大模型被当作苦力，需要处理海量的底层计算和搜索。而在顶级的 AI IDE（如 Cursor、Windsurf）和我们的 `ycc` CLI 中，我们采用**“厚工具层（Fat Tools / Agentic Tools）”**范式。

**核心定律：把确定性的逻辑（AST解析、全盘搜索、特征过滤）全部下沉到本地 Node.js 代码中执行；只把模糊的、需要推理的逻辑（抉择、意图判断）打包交给大模型。**

### 哑工具 vs 厚工具 对比
* ❌ **哑工具模式**：模型调用 `find` -> 工具返回 50 个文件路径 -> 模型循环 50 次调用 `read_file` 寻找特定方法 -> Token 爆炸，模型产生幻觉并死机。
* ✅ **厚工具模式**：模型调用 `semantic_search(class: "User", method: "create")` -> 工具在本地使用 AST 毫秒级遍历 50 个文件 -> 工具精确锁定 1 个目标或 2 个模糊选项 -> 将结果精简后返回 -> 模型轻松做出最终决策。

## 二、 工业级跨文件修改工作流 (The 3-Step Workflow)

当面对“修改一个关联到多个文件的核心方法”这种复杂任务时，坚决不能“把所有代码发给模型重写”，必须遵循极其克制的“三步走”战略：

### 1. 精确制导 (Precise Context Retrieval)
不依赖大模型的肉眼，依赖工具层的硬核技术寻找关联：
* **内存索引 (WorkspaceIndex)**：工具侧维护项目轻量级骨架缓存，极速缩小搜索范围。
* **AST 抽象语法树分析**：利用 `ts-morph` 等库，在工具层解析出类的继承关系、方法的调用链，实现代码级的精确匹配，而非低效的正则匹配。

### 2. 上下文极限压缩 (Context Packing)
找到几十个关联文件后，**按需供给，只给切片 (Snippets)**。
* 工具不返回整个关联文件的源码，只返回目标方法所在的**前后 20 行上下文**。
* 大模型的视野永远聚焦在“刀刃”上，极大地降低了 Token 成本，彻底消灭 Lost in the Middle（中间遗忘）效应。

### 3. 批量判决与人类在环 (Batch Resolution & Human-in-the-Loop)
当工具层遇到无法 100% 确定的情况（例如找到两个同名的方法），工具不应该直接报错退出，而是：
* **整理“单选题”**：工具将所有模糊项打包成一个结构化的列表，一次性提交给大模型做抉择。
* **人工干预兜底**：如果大模型结合用户的全局需求依然无法区分，大模型将调用 `ask_human` 工具。此时，CLI 底层触发 UI 事件总线，在终端渲染 Ink 组件（如 `<SelectInput>`）挂起等待用户抉择，用户选择后图继续流转。

## 三、 `ycc` CLI 的后续开发演进指南

根据此方法论，后续开发应聚焦于以下几个高优组件的实现：

1. **开发 `semantic_search` 工具**：
   引入 AST 解析库，使工具具备理解 TypeScript/JavaScript 语法的能力。允许模型通过“类名”、“函数名”、“导出变量”进行高维搜索。
2. **重构 `WorkspaceIndex` 单例**：
   在系统启动时（或挂载后台 `chokidar` 监听器），生成并维护项目的**骨架地图（Depth-Limited Repo Map）**。大模型通过工具间接查询该地图，解决全局视野与地图过期的问题。
3. **实现 Diff-based 修改工具**：
   在现有的 `edit_file` 基础上，探索接受 `<<<< SEARCH ==== REPLACE >>>>` 补丁语法的工具，使跨文件小幅度修改更加安全高效。
4. **引入 `uiEventBus` 机制**：
   在本地 Node.js 进程中，利用 EventEmitter 和 Promise 挂起机制，实现轻量级的人类在环（HITL）交互，赋予模型主动求助的能力。
