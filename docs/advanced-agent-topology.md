# 📖 Code CLI 多智能体进阶设计笔记：拓扑演进与容错防线

## 一、 多智能体拓扑结构的三种终极形态

在 LangGraph 的编排中，拓扑结构决定了智能体之间的数据流向和控制权。系统的演进必然伴随着拓扑结构的升级：

1. **监管者模式 (Supervisor / Star Topology - 星型拓扑)**
    * **结构**：一个中心化的大老板（Supervisor）作为大脑，所有子节点作为手脚。数据流向永远是 `大老板 -> 员工 A -> 大老板 -> 员工 B`。
    * **适用场景**：任务极度开放、不可预测，需要随时动态改变方向的任务。
    * **痛点**：对于多步骤的重复任务，大老板居中调度的 Token 成本极高，且容易患上“近因效应”（遗忘初始目标）陷入死循环。
2. **流水线模式 (Pipeline / Sequential - 串行拓扑)**
    * **结构**：无中心大脑。任务像工厂流水线一样，从 A 节点强制单向流向 B 节点，再流向 C 节点。
    * **适用场景**：SOP（标准作业程序）非常明确的任务。
3. **层级模式 (Hierarchical / Nested - 嵌套拓扑) 🌟**
    * **结构**：图嵌套图。外层总管将任务派发给一个由流水线或状态机组成的“子图（Sub-graph）”。
    * **适用场景**：工业级复杂系统。这也是我们最终选择的架构终极形态。

## 二、 我们的演进方案：分工解耦与“分析-执行”架构 (Plan-and-Solve)

在面临“一次代码编辑需要循环修改多个文件”的任务时，我们坚决摒弃了“让总管去循环意图识别并分发”的设想，转而采用贴合真实软件工程的 **“先出清单，再循环执行”** 模式。

### 工作流设计：
1. **外层中枢 (Global Graph)**：总管 (Supervisor) 识别宏观需求，将任务整体路由给“重构子图”。
2. **侦察节点 (Analyzer/Explorer)**：
    * **动作**：使用 `list_files` 和 `grep_search` 进行多次内部迭代和信息收集。
    * **输出**：在梳理清晰后，一次性在 State 中输出一个待办队列，例如 `pendingTasks: ["src/form1.tsx", "src/form2.tsx"]`。
3. **执行节点 (Editor/Coder)**：
    * **动作**：从 `pendingTasks` 中提取当前任务，进行代码的读取和修改。修改完成后，状态机流转回路由判断，直到队列清空。
4. **验证节点 (Verifier)**：
    * **动作**：队列清空后，执行测试命令，兜底检查。

## 三、 核心防御防线：破解“智能体死亡循环” (Agentic Loop of Death)

在侦察节点（Analyzer）寻找代码时，极易陷入“找不到 -> 疯狂换词穷举 -> 耗尽 Token”的死循环。必须建立三道容错防线：

### 防线 1：Prompt 层的“连续失败放弃权”（软限制）
在 System Prompt 中明确赋予 AI 放弃的权利，并界定“连续失败”的概念，防止误杀正常的探索。
> **指令规范**：“如果你对【同一个目标】连续尝试了 3 次搜索依然毫无结果，绝对不允许继续盲目猜测。请直接放弃搜索，并在清单外附加说明。”

### 防线 2：状态机的“智能清零计数器”（架构限制）
在 LangGraph State 中引入基于 Reducer 的智能计数器。
* **机制**：在执行工具后，如果工具返回失败，则 `consecutiveFailures + 1`；一旦某次工具调用成功，立即发送 `'RESET'` 信号将其清零。
* **拦截**：在条件路由 (Conditional Edge) 中，一旦 `state.consecutiveFailures >= 3`，强行将图拨向 `END`，终止分析循环。

### 防线 3：物理级的 `recursionLimit`（硬限制）
在调用图的入口处设定物理边界，作为防止 API 费用失控的最后一道硬防线。
* **机制**：通过 `graph.invoke({ ... }, { recursionLimit: 50 })` 或 `streamEvents` 设置最大流转步数。一旦超出，图引擎直接抛出异常并熔断。

## 四、 工业落地盲点与终极解决方案

在构建“出清单 -> 循环执行”的重构子图时，必须跨越以下五个极其隐蔽的工程陷阱：

1. **LangGraph 数组 State 的 `Reducer` 覆盖陷阱**
    * **问题**：如果不对 `pendingTasks` 显式声明覆盖逻辑，底层默认的 Reducer 可能会不断追加（Append）任务数组，导致任务永远执行不完。
    * **解法**：在 State 声明时强制使用覆写：`reducer: (curr, update) => update`。
2. **编辑节点的“上下文滚雪球”与 Token 爆炸**
    * **问题**：在循环编辑多个文件时，如果带着前面所有文件的修改历史继续执行，会导致严重的上下文过载和幻觉。
    * **解法**：实现**无状态执行 (Stateless Worker)**。编辑节点每次被唤醒时，它的 `localMessages` 必须清零，只传入“宏观任务”和“当前这单个文件的路径”。
3. **行号偏移灾难 (The Line-Shift Problem)**
    * **问题**：如果分析员在清单中记录了绝对行号（如“修改第 10-20 行”），一旦前置任务修改了同一文件或相关文件，行号就会偏移，导致后续编辑直接删错代码。
    * **解法**：推迟精准定位的时机。清单中**只存文件路径**，绝生存行号。编辑员必须遵循“修改前必读 (READ BEFORE WRITE)”规则，现场使用 `read_file` 获取最新行号后再调用 `edit_file`。
4. **跨文件依赖的“幽灵上下文”**
    * **问题**：处理后一个文件时，编辑员不知道前一个文件已经提取了某些公共逻辑，导致重复造轮子。
    * **解法**：引入全局的 `changelog`（变更日志）。编辑员每次改完代码，提炼一句话摘要写入全局 State。下一次唤醒时，将这份摘要作为只读上下文注入 Prompt。
5. **局部失败的处理机制 (Partial Failures)**
    * **问题**：遇到超复杂文件改不出来，或者 Verifier 测试报错，如果死磕会导致整条流水线崩溃。
    * **解法**：引入“重试与搁置”机制。给编辑节点加入容错阈值，修改 3 次依然失败的文件，将其从 `pendingTasks` 移出并推入 `failedTasks` 数组，流水线继续前进。最终让总管或人类看着 `failedTasks` 决定下一步动作。
